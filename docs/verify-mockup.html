SafeAgent Verify — concept preview

What a duplicate-execution scan report would look like.

SafeAgent Verify is a planned scanner that would probe any live API endpoint for duplicate-execution safety — retry races, missing idempotency keys, webhook replay handling — and return a report like the one below. This page shows example output only. No scan has been run and no such tool exists yet.

Findings

✗ Retry race: 2 concurrent identical requests produced 2 distinct side effects FAIL
Two identical POST /orders requests fired at the same instant both went through as separate orders instead of one being rejected or deduplicated. This is the classic double-submit failure — a slow network or a retrying client can silently double a charge or a trade with no error surfaced to the caller.
✓ Idempotency-Key header respected on POST /charge PASS
Sending the same Idempotency-Key value twice on POST /charge correctly returned the original response on the second call instead of creating a new charge. This is the standard pattern (as used by Stripe) and it's implemented correctly here.
✗ Timeout-then-retry produced a duplicate within 400ms window FAIL
Simulating a client that times out waiting for a response and retries the same request 400ms later resulted in the action executing twice. In production this is exactly the scenario that causes double-charges and double-sends when a network hiccup makes a client believe a request failed when it actually succeeded.
✓ GET/DELETE correctly idempotent PASS
Repeating GET /orders/:id and DELETE /orders/:id multiple times produced consistent, side-effect-free results as expected for these HTTP methods. No issues found here — this is the baseline behavior the spec requires.
✗ Webhook replay (same event ID redelivered) not deduplicated FAIL
Redelivering the same Stripe-style webhook event ID to POST /webhooks/stripe triggered the downstream handler a second time. Since providers like Stripe, GitHub, and Twilio all guarantee only at-least-once delivery, a webhook receiver that doesn't dedupe on event ID will double-process any event that gets redelivered.
✓ Error responses precede any side effect (fail-safe ordering) PASS
When a request was malformed or failed validation, the server rejected it before touching any downstream system — no partial writes or dangling side effects observed on the failure paths that were probed. Good defensive ordering.
